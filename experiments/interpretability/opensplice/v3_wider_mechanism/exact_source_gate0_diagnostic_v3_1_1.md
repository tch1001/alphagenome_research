# Exact-source Gate-0 diagnostic v3.1.1

**Design date:** 2026-08-28

**Status:** prospective, identity-only development diagnostic; freeze this
document and the diagnostic launcher hashes before any GPU execution

**Source under test:** pristine commit
`fd4dc6913335a6966420d60ef04bc4643b751a27`

**Scope:** the 20 frozen BRAF e14 and SLC25A48 e8 development rows, in their
frozen order, exactly once

**Confirmation status:** blind; no ELN, EIF4A2 or DMD sequence, prediction,
target, activation or intervention may be loaded

## 1. Purpose and non-purpose

The v3.1 exact-current-source Phase-R reference passed the first two BRAF
identities but stopped on `BRAF_e14_T71G`. Its six absolute target differences
from the locked Phase-R identity were

```text
[0.00390625, 0.014404296875, 0.014404296875,
 0.014404296875, 0.00390625, 0.00390625].
```

The frozen inclusive per-value tolerance remains
`2^-8 = 0.00390625`. The first two identities and all three rows for the same
allele were exact within their current compiled execution. No v3.1 Stage-A
identity or active component ran.

v3.1.1 asks one bounded question: **can a new execution from the exact source
commit that produced the locked Phase-R study reproduce all 20 saved identities
under the unchanged checks?** It is a source/runtime diagnostic, not a retry of
v3.1, a Stage-A experiment, or a mechanism result. Passing cannot reclassify
v3.0.2 or v3.1, authorize an active patch, or show which compiler mechanism
caused either failure.

A pre-inference dry run exposed one build-provenance limitation. Commit
`fd4dc69...` tracks
`src/alphagenome_research/protos/calibration_scores.proto` but intentionally
does not track its generated `calibration_scores_pb2.py` or `.pyi` bindings.
The locked historical run and the current checkout could import `dna_model`
only because a generated binding existed as an untracked build-hook output in
their working environment. The Phase-R lock did not serialize the exact
historical generated bytes, compiler version or generation command. v3.1.1
therefore cannot claim byte identity to that historical build artifact. Section
3 prospectively permits one narrowly defined regeneration from the exact
tracked proto and requires its full provenance. This disclosure was added
before v3.1.1 model creation or GPU inference.

## 3. Exact-source isolation

The compilation path must come from a clean, detached worktree at the full
`fd4dc69...` commit. The diagnostic launcher may live outside that worktree.
It must not patch or copy model/runner source into it. The sole permitted
untracked source-tree preparation is generation of the two protobuf bindings
specified in Section 3.1 from the worktree's exact tracked proto. Before
importing JAX model modules, the launcher must:

1. assert the worktree HEAD is exactly `fd4dc69...` and its tracked diff is
   empty;
2. verify the original Phase-R runner, v2 runner and every compilation-path
   source digest against the digests serialized in the locked identities;
3. generate and validate the declared protobuf bindings exactly as specified
   below, then reassert that the tracked diff is empty and that no untracked
   files other than the two allowlisted bindings exist before import;
4. remove the current checkout from module search resolution and inventory
   every imported AlphaGenome Research, AlphaGenome and OpenSplice module,
   including transitive protobuf, model, data, I/O and utility modules rather
   than only a hand-written top-level allowlist;
5. for every file-backed module, record its module name, resolved `__file__`,
   size and SHA-256; for a namespace or built-in module without `__file__`,
   record that fact and its resolved package search paths;
6. require every `alphagenome_research.*` and OpenSplice helper to resolve
   inside the exact-source worktree, and every declared third-party
   `alphagenome.*` module to resolve inside one recorded AlphaGenome package
   root; and
7. abort before model creation if the initial inventory violates containment.
   Repeat the inventory after model construction but before lowering/compile,
   and at cohort completion, so a lazy import cannot evade the same containment
   and hash record. A post-start containment failure is terminal and consumes
   the one-shot attempt without running an apply call.

## 4. Exactly one cohort attempt

There is one output directory and one cohort attempt identifier. The launcher
must refuse to start if that attempt directory already contains an attempt.
Before model creation it atomically writes an append-only start record with
the wall-clock time, launcher/protocol/source hashes and pre-run provenance.

"Each identity once" means one identity unit per development row in this one
cohort attempt. The identity unit retains the original two calls required to
test an exact warm repeat; it does not mean deleting that repeat call. There
are therefore exactly 20 identity units and 40 all-false apply calls, barring a
terminal runtime failure. There are:

- zero active Phase-R residual groups;
- zero Stage-A graph constructions or calls;
- zero attribution, ranking or mechanism selection calls; and
- zero confirmation model calls.

All 20 development identity units are attempted even after an ordinary
per-case numerical or validation failure. A failed case is diagnostic data and
must not stop later development identities from being recorded. Only a
terminal condition that makes further execution unsafe or impossible, such as
process termination, checkpoint-load failure, device loss or unrecoverable
accelerator error, ends the cohort early.

There is no resume, deletion, overwrite, rerun, second seed, second compiler
configuration or replacement cohort. A terminally interrupted attempt remains
partial and failed. Any later execution requires a separately designed and
versioned prospective protocol; it cannot reuse the v3.1.1 name.

## 5. Required per-case artifacts

Write one append-only raw artifact for every attempted case **before** applying
the cohort-level decision. A target mismatch must never raise before its raw
record is durable. Each artifact contains at least:

- attempt ID, frozen case order/ID/gene/class and locked identity fingerprint;
- all input-linkage fields and whether each matched exactly;
- the six locked target means and six current target means in frozen role
  order;
- signed and absolute `current - locked` differences for all six roles;
- current and locked ALT-minus-REF margins, experimental direction and the
  `0.01` effect-denominator/direction checks where applicable;
- exact first-versus-second target/trace repeat checks;
- exact natural duplicate REF rows `0/4/5` and ALT rows `1/2/3` checks;
- first compile/run and warm-repeat durations;
- a status of `pass`, `numerical_failure`, `validation_failure` or
  `runtime_failure`; and
- for a failure, its stage, exception type and complete message without
  discarding already materialized numerical values.

Artifacts must be atomic and immutable after publication. At cohort end, write
a summary with attempted/pass/failure counts, the ordered status of all 20
rows, whether the cohort passed, every artifact SHA-256 and a deterministic
artifact-tree SHA-256. A terminal process failure may prevent the final
summary, so the start record and completed per-case artifacts must independently
show that the attempt is partial.

## 6. Compiler and machine provenance

Record provenance before the first apply call and again at cohort completion:

- OS/kernel, hostname, process ID, Python and NumPy;
- JAX, jaxlib, JAX CUDA plugin, CUDA runtime/toolkit, cuDNN and relevant
  cuBLAS versions;
- GPU model, UUID, compute capability, VBIOS, driver and visible-device order;
- exact `XLA_FLAGS`, `JAX_*`, `CUDA_*`, `NVIDIA_*` and other compiler/cache
  variables used by the launcher, with secrets excluded and unset variables
  represented explicitly;
- JAX default precision and mixed-precision policy;
- compilation-cache and autotune-cache configuration, locations, pre-existing
  state, observable hit/miss state and hashes when the installed stack exposes
  them; and
- pre-optimization StableHLO, optimized HLO, backend configuration, executable
  or autotune-result hashes when available without changing the tested graph.

Failure to obtain an HLO or autotune artifact is recorded as `unavailable`
with the reason. It does not permit a rerun and does not by itself fail target
identity. Conversely, matching HLO text does not prove identical backend
kernels, and a different HLO hash does not identify which optimization caused
a numerical difference.

The mixed-precision record is not inferred only from output dtypes. It must
bind the exact factory
`create_splice_classification_logit_margin_route_census_apply`, the locked
`src/alphagenome_research/model/dna_model.py` digest, and the literal policy

```text
params=float32,compute=bfloat16,output=bfloat16
```

used by its `jmp.get_policy` call. Record that literal, the resolved runtime
policy representation and the `jmp`/Haiku package versions before lowering.
Any mismatch fails before compilation; the diagnostic must not set a new
policy to make the check pass.

## 7. Frozen decision rule

An individual identity passes only if all of the following hold:

1. input linkage is exact;
2. both calls complete and target plus compact trace repeats are bit-exact;
3. natural same-allele duplicate rows are bit-exact;
4. every one of the six current target means satisfies the unchanged inclusive
   rule `abs(current - locked) <= 2^-8`; and
5. for an effect row, both locked and current ALT-minus-REF magnitudes are at
   least `0.01` and have the frozen experimental sign.

The v3.1.1 cohort passes only if all 20 identities pass. There is no percentage
allowance, rounding, ULP reinterpretation, averaged error, signed-error
cancellation or exception for neutral rows. The launcher collects all rows but
makes the single cohort decision only after the twentieth attempt. It then
stops unconditionally: even a passing cohort cannot transition to active
inference.

## 8. Interpretation and claim boundary

### If all 20 identities pass

Allowed claim:

> In one prospectively bounded execution on the recorded software/compiler
> stack, the pristine original Phase-R source reproduced all 20 locked
> development identities within the unchanged `2^-8` criterion and passed its
> exact within-executable controls.

This makes source-tree or compilation-context differences a plausible subject
for further diagnostics. It does **not** prove that the additive Stage-A source
caused the v3.1 miss, prove compiler determinism, validate Stage A, rescue a
previous failure, or authorize any active or confirmation execution.

### If any identity fails the numerical or validation rule

Allowed claim:

> The pristine original Phase-R source did not reproduce the complete locked
> development identity cohort in this one recorded execution.

The location and magnitude of the persisted differences may motivate a new
prospective compiler diagnostic. They do not identify a hardware defect, a
specific XLA/autotune algorithm or stochastic BF16 behavior. v3.1 remains
failed and no active work is authorized.

### If the attempt is partial or has a runtime failure

The result is an incomplete tooling diagnostic, not a pass or a biological
negative. Completed artifacts remain reportable as tooling observations, but
the cohort fails by definition and is not resumed.

Under every outcome, the locked Phase-R biological result remains a separate
historical result, the v3.0.2 and v3.1 Gate-0 failures remain in the record,
confirmation remains blind, and the next substantive experiment requires its
own prospective design.
